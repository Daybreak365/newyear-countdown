# 새벽별 런타임 확장 (1.2.4)

## 1.2.4: 미리보기부터 완공까지 같은 설계로 연결

- 최초 `preview_blocks`가 블록 목록·절대 좌표·차원·설계 ID/버전을 소원에 저장한다. 같은 소원에서 다시 요청하면 새로 생성한 코드나 플레이어의 현재 위치를 사용하지 않고 저장된 설계를 다시 보여준다. 계약 카드에도 고정 위치를 표시하고, 수락은 해당 설계 ID/버전에만 적용된다.
- 수락 뒤 조건 목표들과 `build` 목표가 있는 퀘스트를 한 번 만든다. 조건 추적 스크립트에서 즉시 `construction.start(questId, 'build')`를 호출하면 서버 전용 시공 작업이 준비된다. 나머지 필수 조건이 완료되면 저장된 블록 목록을 FIFO로 배치한다. AI가 조건 완료 시 부지를 다시 계산하거나 별도의 건축 코드를 만들지 않는다.
- 부지에 사람·동물이 있거나 보호된 블록·로드되지 않은 청크 때문에 배치할 수 없으면 `WAITING_SITE`에서 같은 칸을 기다린다. 조건과 작업 위치를 유지하고, 막힌 이유와 좌표를 안내한다. 완료한 조건을 초기화하거나 다시 계약하도록 만들지 않는다. 추적 스크립트 교체로 퀘스트가 취소되는 것도 막는다. 플레이어의 명시적 소원 취소는 적용된다.
- 시공 완료 판정은 저장된 모든 칸의 블록 종류와 배치 방향을 확인한다. 울타리 연결·계단 모양처럼 주변 블록에 따라 바뀌는 속성은 허용한다. 확인 전에는 생성 코드가 `build` 목표나 소원을 임의로 완료할 수 없다.
- 설계·위치 변경은 `revise_build_plan`의 별도 변경 확인을 수락해야 적용된다. 확인 전까지 기존 설계가 유지되며, 확인 후에도 기존 조건 진행을 보존한다. 이미 시공을 시작한 설계는 교체하지 않는다. 같은 소원의 반복 미리보기·계약·퀘스트 생성 요청은 기존 항목을 재사용한다.
- 4096칸을 넘는 미리보기는 잘라 저장하지 않고 오류로 알린다. 고정 설계는 영구 블록으로 작성하며, 임시 블록이나 실제 결과가 확정되지 않은 나무 생성의 간략 미리보기는 설계로 저장하지 않는다. 나무를 포함하려면 원목·잎 좌표를 설계에 명시한다. 기존 서버의 관리자 승인 기준도 시공 작업에 유지된다.

`construction.status()`로 설계·수락 여부·고정 범위·진행 상태·대기 이유·조건 퀘스트·시공 작업 ID를 조회한다. 설계와 작업 커서는 정상 저장 후 재시작해도 유지된다. 이 버전은 저장된 설계가 없는 과거 실패 계약이나 이미 차감한 임의 스크립트 상태를 자동 수정하지 않는다. 기존 계약을 복구할 때는 완료 기록과 합의한 위치를 먼저 확인해야 한다.

게임 내 확인 순서: 집 미리보기 → 다른 위치로 이동하여 같은 설계 다시 보기 → 수락 → 조건 일부 완료 후 재접속 → 나머지 조건 완료. 도중 부지를 가로막으면 실패·이동·조건 초기화 대신 같은 위치에서 대기하고, 장애물을 치우면 이어서 시공해야 한다. 별도 변경 확인을 거절했을 때 기존 미리보기가 유지되는지도 확인한다.

## 1.2.3: 건축 실행 오류와 부지·미리보기 진단

- `state.waiting = null`처럼 정상적인 null 값이 객체·배열·클로저에 있을 때 메모리 검사기의 `ArrayDeque.push`가 예외를 내던 문제를 수정했다. 메모리 검사도 사전 검증에 포함하고, 활성화 단계의 검사는 오류 처리 범위 안에서 수행한다.
- `world.checkBlock(pos, block, opts?)`는 실제 배치 정책을 읽기 전용으로 검사하고 `{allowed, current, reason}`을 돌려준다. 건축터 전체가 공기인지 검사하는 대신 자연 지형·풀·보호된 블록을 실제 규칙으로 구분할 수 있다. 지반 지지와 플레이어·엔티티의 위치는 별도로 확인해야 한다.
- 점진적 작업의 검증에서 배치가 거부된 칸을 조용히 빼고 성공으로 보고하지 않는다. 거부된 칸 수와 최대 8곳의 좌표·이유를 오류로 제공한다. 이미 원하는 블록 상태인 칸은 실제 실행과 동일하게 변경하지 않는다.
- 미리보기는 검증 성공, 비어 있는 계획, 실제 오버레이 패킷 전송, 모드 없는 클라이언트의 채팅 요약을 구분한다. `preview_sent:true`는 패킷 전송 근거이며 실제 화면 렌더링 수신 확인을 의미하지 않는다. 마지막 전송 결과·좌표·차원과 최근 시도 결과를 소원에 저장하고 다음 AI 턴에 전달한다.
- AI 지침에 승인된 위치 재사용, 이동 후 임의 재선정 금지, 같은 설계 반복 승인 방지, 완료한 대가 조건 유지, 구체적인 부지 거부 이유 안내를 추가했다. 기존에 생성된 스크립트를 자동으로 다시 쓰지는 않는다.
- `world_edit_done`에 `unchanged`, `total`, `complete`를 추가했다. 이미 목표 상태인 칸과 이번에 실제로 바꾼 칸을 구분한다. `placed !== total`만으로 실패를 판정하면 안 된다. 블록 변경 실패와 사라진 차원의 남은 작업도 실패 수에 포함한다.

이번 로그의 오두막 계약은 원목 목표 16/16, 건축 0/1에서 종료됐다. 기존 실패한 소원·퀘스트·월드 저장 파일은 변경하지 않았다. 업데이트 후 복구할 때 이미 달성한 원목 조건과 사용자가 확정한 좌표를 그대로 사용해야 한다.

## 1.2.2: 대화 순서, 검증 격리, 건축 대기열

- 전송 직후부터 답변과 도구 처리가 끝날 때까지 입력·빠른 답·새 소원·계약 선택을 잠근다. 서버에서도 `/wish`, 연등, 패킷 입력을 같은 플레이어 단위로 검사한다. 처리 중인 입력을 몰래 다음 턴으로 합치지 않는다.
- 같은 플레이어의 스크립트·자동 알림은 원래 종류와 소원 ID를 유지한 대기열에서 처리한다. 취소된 턴의 늦은 도구 실행·답변은 폐기하며, 예전 완료 콜백이 새 대화의 잠금을 풀 수 없다. 오류·취소·킬 스위치에서 잠금을 해제하고 재접속 시 서버 상태를 동기화한다.
- 계약의 응답 제한 시간은 새벽별이 답변 중일 때 멈춘다. 답변 종료 후 남은 시간을 다시 동기화한다.
- 검증의 `quests.get/active/create`와 이벤트의 퀘스트 핸들은 검증 인스턴스 안의 복사본을 공유한다. 검증에서 목표를 달성·실패·완료해도 실제 퀘스트, 결제 목표, 보상 이벤트는 변경하지 않는다.
- `world.box/sphere/replace/clear/terraform`은 저장되는 FIFO에 들어가 하나씩 실행된다. 기존 4개 동시 작업 제한을 없애고 최대 256개 대기 작업과 전체 남은 블록 수를 함께 제한한다. 기록된 블록 + 대기 블록 합계는 `scriptMaxBlocks * 2` 이하여야 하며, 검증에서도 같은 규칙을 적용한다. 틱당 처리량·건축 보호 정책은 유지한다.
- `world.edits()`는 `state: running/queued`도 반환한다. 빈 작업도 완료 이벤트를 보내고, 일회성 건축은 작업이 끝나기 전 종료하지 않는다. 여러 작업을 요청한 뒤에는 모든 ID의 `world_edit_done`을 확인해야 완공이다.
- 타이머를 시뮬레이션하지 않은 검증에는 경고를 표시한다. 조건을 여는 이벤트까지 테스트해야 하며, 검증 성공만으로 실제 완공이나 결제를 선언하면 안 된다.

계약 아이템 대금은 `payments.charge('house_cost', 'dirt', 64)`로 기록한다. 반환값이 true일 때만 결제 목표를 진행한다. 같은 소원 안의 동일 키는 정상 저장·재시작 후에도 중복 차감하지 않는다. 이름·커스텀 구성 요소가 없는 일반 아이템만 사용한다.

`payments.get('house_cost')`로 영수증을 확인하고, `payments.refund('house_cost')`로 실제 차감 후 미반환 잔액만 돌려준다. 반환값은 이번에 돌려준 수량이다. 이전 소원의 환불에는 컨텍스트의 `payment_receipts`에 나오는 전체 영수증 ID를 사용한다. 영수증이 없거나 이미 환불했다면 0이며, 다른 플레이어의 영수증으로 환불할 수 없다. 검증은 별도 영수증 복사본만 사용한다. 과거 `owner.take/give` 내역으로 영수증을 추측해서 생성하지 않는다.

새 버전은 게임 프로세스를 완전히 종료한 뒤 실행해야 적용된다. 이미 생성된 스크립트의 임의 상태 변수(예: `failBuild=true`)는 자동 초기화하지 않는다. 이전 버전에서 멈춘 건축 계약은 새벽별에 실패 기록을 확인하고 재시도하도록 요청해 복구해야 한다.

## 1.2.1: 능력 배정과 코드 교체 안정화

- 실행 인스턴스가 자신의 소스 원본을 보관한다. AI 수정·관리자 편집·되돌리기 중 공유 기록의 코드가 바뀌어도 이전 콜백을 새 코드의 저장본으로 기록하지 않는다.
- `controls.assign(player, action, label)`은 빈 슬롯을 찾는다. 같은 플레이어·액션의 기존 슬롯을 유지하고, 수정 시에도 가능한 한 유지한다. 다른 능력의 슬롯은 덮어쓰지 않으며 일시정지한 능력의 예약도 존중한다.
- 발동 방법을 지정하지 않은 능동형 소원은 `controls.assign`을 기본으로 사용하도록 AI 지침을 보완했다. 패시브·조건부 능력과 사용자가 지정한 조작은 해당 발동 방식을 유지한다.
- 키만 배정하고 `ability_input` 처리기를 빠뜨린 코드는 검증 및 활성화 단계에서 실패한다. 코드 교체 때 삭제된 액션의 슬롯이 남지 않도록 정리한다.
- AI·관리자 조회는 실제 실행 중인 리스너 수를 사용한다. 물리 키가 미지정인 경우 HUD에 조작 설정 안내를 표시한다.
- `player.push`는 Minecraft의 `syncVelocity`를 설정하여 조종 중인 본인 클라이언트에도 속도를 전달한다. `/wishai selftest`에 바닐라 패킷 전송 경로를 검사하는 진단을 추가했다.

이 변경은 공통 런타임과 새로 생성·수정되는 능력에 적용된다. 특정 소원 스크립트나 월드 저장 파일을 개별 수정하지 않는다. 이미 손실된 콜백 기록을 추측해서 복원하지도 않는다.

소원마다 Java 기능을 추가하지 않고 WishScript에서 아이템, 사건, 이동, 투사체, 체크포인트, UI를 조합한다. 부족한 엔진 기능은 AI가 Java 확장 초안을 작성하고, 운영자가 격리 테스트와 코드 검토를 거쳐 설치한다.

## 즉시 사용할 수 있는 구성 요소

| API | 동작 |
| --- | --- |
| `items.components/get/patch` | 현재 Minecraft 레지스트리의 허용된 구성 요소를 조회·수정. 인챈트, 도구·소비·장비 동작, 외형 등. 바닐라 codec과 아이템 전체 유효성 검사를 통과해야 적용 |
| `owner.give(...,{components:{...}})` | 같은 구성 요소를 적용해 아이템 생성 |
| `owner.takeXpLevels(n)` | 동의된 대가로 XP 레벨 차감, 부족하면 false |
| `before_damage/death/item_use/attack/block_break` | 사건 발생 전에 `{cancel:true}` 반환으로 개입. 피해량 변경은 `before_damage`의 `{amount:n}` |
| `attributes.list/get/modify/remove` | 중력·이동 속도·크기 등 실제 레지스트리 속성 수정. 스크립트 종료/일시정지 시 해제, 재개/재접속 시 복구 |
| `projectiles.fire/remove` | 입자 투사체, 중력·유도·선분 충돌. `projectile_hit`에서 피해·밀치기·효과 등 작성 |
| `snapshots.capture/restore/discard` | 위치·체력·허기·선택적 장비 상태의 일회용 체크포인트. 같은 차원과 안전한 위치만 복구. 사라지거나 이동한 장비를 재생성하지 않음 |
| `controls.assign/bind/panel/clear` | 빈 슬롯 자동 배정 또는 명시적 슬롯 선택, 능력 키 4개와 HUD. 초기 물리 키는 미지정이므로 Minecraft 조작 설정에서 선택 |
| `content.create` | AI가 저장한 버전 고정 팩터리를 실행. 생성 효과의 수명·권한·예산은 호출한 스크립트에 귀속 |
| `extensions.list/call` | 운영자가 설치한 Java 확장의 연산 조회·호출 |

기존 영역 이벤트·타이머·3D 모델·텍스처·몹 목표·brain과 함께 사용한다. AI 도구 `get_capabilities`, `get_script_api`에서 실제 API와 예시를 조회할 수 있다. 슬롯은 `mainhand/offhand/head/chest/legs/feet` 또는 인벤토리 인덱스다. 구성 요소의 값은 실행 중인 Minecraft 버전의 JSON 형식이다.

시작 코드는 재시작 때 다시 실행된다. 생성·체크포인트는 `state`로 중복을 막고 이벤트 리스너는 매번 등록한다. 속성·HUD·투사체·체크포인트는 엔진 전용 `runtime` 데이터로 저장된다. 킬 스위치는 능력의 입력과 피해 개입을 중단한다. 반환값 기반 사건 개입은 실패한 핸들러의 반환값을 버리며, 핸들러가 이미 수행한 별도 세계 변경까지 되돌리는 트랜잭션은 아니다.

## 재사용 콘텐츠

`publish_content`에 `name`, `description`, `code`를 전달한다. 코드는 `params`를 인자로 받는 함수 본문이다. 결과 ID는 `소유자UUID/이름@버전`이다. 다른 플레이어의 비공개 팩터리는 가져올 수 없다.

```javascript
// @use 반환된-정확한-ID
const ability = content.create('반환된-정확한-ID', {power: 2});
```

초안 작성 시 팩터리 소스가 스크립트에 포함된다. 나중에 새 버전을 게시해도 기존 능력은 바뀌지 않는다. 최대 8개 팩터리를 가져오며 중첩 가져오기는 지원하지 않는다.

## Java 확장 경로

1. AI가 `get_script_api(topic:"native")`를 읽고 `draft_extension`을 호출한다. Java 25 단일 소스와 선택적 JSON 리소스를 작성한다. 중첩 클래스는 가능하다.
2. 서버는 별도 javac 프로세스에서 어노테이션 프로세서를 끄고 컴파일한다. 이 단계에서 생성 코드를 실행하지 않는다. 실패 로그는 `get_extension`으로 전달된다.
3. 운영자가 `/wishai extension ID`로 코드·SHA-256·상태를 검토하고 `/wishai extension ID test`를 실행한다.
4. 설정된 격리 실행기가 별도 Minecraft 월드에서 `selfTest`와 `integrationTest`를 실행한다. 보고서는 파일 해시와 참/거짓 단언을 포함해야 한다. 설정이 없으면 `NEEDS_INTEGRATION_TEST`에 머문다.
5. 통과한 **동일한 파일**을 `/wishai extension ID approve 전체SHA256`으로 승인한다. 일반 `NativeExtension`은 즉시 로드된다.
6. 레지스트리 등록·믹스인·클라이언트 초기화가 필요한 확장은 `fabric.mod.json`을 포함한다. 승인 후 `/wishai extension ID stage`로 mods에 배치하고 서버와 필요한 클라이언트를 재시작한다. 서버 명령이 클라이언트에 모드를 설치하지는 않는다.

`/wishai extension ID disable`은 사용 중인 스크립트를 정지하고 일반 모듈을 해제한다. 재시작용 모드의 배치를 취소하거나 제거한 경우에도 이미 실행 중인 모드가 사라지려면 재시작해야 한다. 모듈의 `close()`와 `ctx.onStop(...)`은 자신이 만든 후크·작업·효과를 정리해야 한다.

SPI와 실제 입력 검증·게임 단언 예시는 [examples/Momentum.java](examples/Momentum.java)에 있다. 네이티브 코드는 설치 후 전체 JVM 권한을 갖는다. WishScript의 단계 예산이 Java의 무한 루프나 외부 작업을 중단시키지 못하므로 테스트 통과만으로 자동 설치하지 않는다. 모든 새 기능이 무재시작으로 가능하다는 의미는 아니다.

## 격리 게임 테스트 실행기 설정

제공된 [../tools/extension-runner.py](../tools/extension-runner.py)는 Docker를 사용한다. 운영자가 Python 3, 실행 중인 Docker, 로컬에 준비한 Java 25 이미지, Minecraft 26.3/Fabric의 오프라인 부팅 가능한 테스트 서버 키트를 준비한다. 외부 이미지 다운로드와 EULA 동의는 자동으로 수행하지 않는다.

키트에는 실행 가능한 Fabric 런처 `server.jar`, 이미 동의한 `eula.txt`, 해당 버전의 `libraries`와 `mods`(새벽별 1.2.0 및 Fabric API)를 둔다. 필요한 경우 `.fabric`, `versions`, `fabric-server-launcher.properties`도 허용한다. 실제 월드·사용자 설정·계정 자료는 넣지 않는다. 컨테이너는 네트워크 없음, 읽기 전용 루트, 권한 제거, CPU/메모리/PID/시간 제한으로 실행되고 월드는 임시 저장소에 생성된다.

`config/newyearcountdown-ai.json` 예시(실제 절대 경로와 로컬 이미지 이름으로 교체):

```json
{
  "extensionTestCommand": [
    "C:/Python/python.exe", "C:/server/tools/extension-runner.py",
    "--kit", "C:/server-test-kit", "--image", "local/java25:tested",
    "--jar", "{jar}", "--report", "{report}", "--hash", "{hash}",
    "--class-name", "{class}", "--restart", "{restart}"
  ]
}
```

기존 설정의 다른 키는 그대로 두고 이 필드만 추가한다. `/wishai reload` 후 테스트 명령을 실행한다. 실행기는 호스트 서버의 API 키를 전달받지 않는다. 별도 컨테이너/VM 실행기가 있다면 같은 명령 인자와 보고서 규약으로 교체할 수 있다.

## 검증

일반 개발 환경: `./gradlew test build` (Java 25). 이 작업 환경의 Windows 경로 조회 권한 문제로 Gradle/Loom이 시작되지 않아, 같은 버전의 캐시 의존성을 추출해 전체 소스를 javac로 컴파일하고 JUnit을 실행하는 `tools/verify-runtime.ps1 -Test`도 제공한다. 검증용 디렉터리는 `build/verify`이며 게임 런타임에는 이 우회 코드가 포함되지 않는다.

`/wishai selftest`에는 구성 요소 변경, 체크포인트, 속성 정리, 능력 입력의 소유자 검증, 피해 개입 진단이 추가되었다. 실제 서버와 클라이언트에서 HUD·키 설정·재접속·재시작·믹스인 동작도 확인해야 한다. 현재 환경에서는 Docker 데몬이 실행되지 않아 이 게임 통합 검증은 실행하지 못했다.
